07 — Persona-Aware Retrieval

Same category, different Item number per filing type

Retrieval is filtered to the canonical categories each persona actually cares about, before any similarity search runs — not to raw 10-K Item numbers.

PersonaCares aboutCanonical categories
LegalLitigation, compliance risklegal_proceedings · risk_factors
Audit FirmFinancial statements, internal controlsfinancial_statements · controls_procedures
Investment FirmPerformance drivers, outlookmdna · financial_statements
Investment BankCapital structure, debt, M&Amdna · market_risk · financial_statements
TreasuryLiquidity, cash flow, FX exposuremarket_risk · financial_statements

why it mattersMD&A is Item 7 in a 10-K but Item 2 in a 10-Q — and a 10-Q reuses Item 1 twice with different meanings in Part I vs. Part II. Filtering on the category instead of the number is what lets the same persona table work for both filing types without a second set of rules.

on retrywidens to a fixed fallback — risk_factors · mdna · market_risk · financial_statements — instead of reformulating the query. Simpler, and it attacks the most likely cause: a persona filter that was too narrow.

09 — Beyond the Fixed Corpus

Two ways in: ask about it, or drop the file

Sister features, same processing pipeline underneath — they differ only in where the filing comes from.

Dynamic ingestion

A question naming a company that isn't indexed triggers check_entity_exists to fetch its latest 10-K from SEC EDGAR mid-request, before retrieval runs.

Entity resolution runs in two tiers — corpus match first, then an LLM + EDGAR's public ticker mapping only when that finds nothing, so a normal question about Apple never pays for an extra LLM call.

8m14sNVDA, live
~11×cost vs normal

Document upload

Drop a 10-K/10-Q .html in the sidebar — POST /documents/upload validates it in two steps before indexing anything.

1. Is it even a real EDGAR filing? Checked against the standard inline-XBRL dei:* tags every modern filing carries. 2. Does it have all 6 canonical sections after parsing? Either failure returns status: error — nothing partial is ever written.

asyncbackground job

10 — What Broke, and Why (1/2)

Thirteen real bugs, found by running it

Every one below was caught by executing the pipeline against live data or reading actual retrieved text — never by reading the code and assuming it was right.

Parsing

sec-parser has no 10-K parser

Only ships an Edgar10Q classifier — fixed by extracting sections on the title regex instead, relaxed for filers (Google) that omit the trailing space.

Models

Two models retired mid-project

gemini-embedding-2 and gemini-2.5-* both 404'd — caught by calling the API directly, not trusting models.list().

Critical

Retry loop never terminated

A router function mutating state doesn't persist in LangGraph — retry_count stayed at 0. 300+ loop iterations, stopped only by Google's own rate limit.

Response shape

qdrant's query_points wraps its result

Returns a QueryResponse, not a bare list — RRF fusion needs .points extracted first.

Observability

Trace ID was always null

LangSmith's run context only exists inside a traced call — @traceable on handle_query fixed it.

Comparison queries

No named company, no chunks

"risk factors 2024 vs 2025" names no company — retrieve_multi now falls back to every ticker in the corpus.

11 — What Broke, and Why (2/2)

...and seven more, found building dynamic ingestion

28% of corpus

Contextual retrieval named the wrong company

doc_id never reached the prompt — the model guessed, and guessed "Apple" often enough to mislabel 45% of GOOGL chunks and 33% of MSFT. Found reading real retrieved text in the UI.

Prompt compliance

Model replied "here are two options"

Even given the right identifier, a conversational prompt got meta-commentary back, not one sentence — 146 chunks had it embedded. Fixed with a strict single-output instruction.

Silent resolution failure

"Tesla Inc" ≠ "Tesla, Inc." to a string compare

Punctuation/suffix mismatch between an LLM's extraction and EDGAR's title silently dropped the company — no error, no banner. Fixed with a shared normalizer.

Resilience

One LLM hiccup could kill an unrelated query

Tier-2 resolution runs on any question without a known company — an unguarded exception there took the whole query down. Now it degrades to a trace note.

Data migration

A "safe" migration order wasn't

Delete-then-reinsert, interrupted mid-insert by the machine sleeping, left a real gap — 35 chunks gone. Rewritten insert-first, delete-after: interruption now leaves redundant data, never a hole.

Parser drift

MSFT parsing changed since it was first ingested

Re-parsing the same static HTML today yields ~5,000 fewer characters than originally — found only because a remediation script's compare step exposed it.

Test rot

The E2E suite was silently broken

A translation pass changed the DOM text every selector searched for — 3 "passing" tests were actually hitting a stopped Docker container's stale build, not the new code.
